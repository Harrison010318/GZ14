# GZ-14 游戏后台（局外系统）需求分析文档

> 项目：游戏后台技术研究——局外系统  
> 目标：设计并实现一个简易的游戏后台服务，包含角色创建、登陆下线、移动同步功能

---

## 一、技术场景分析

### 1.1 业务场景概述

本系统为一个 **MMO 类型游戏的局外后台服务**，核心场景如下：

| 场景 | 描述 | 关键指标 |
|------|------|---------|
| 角色管理 | 创建角色、存储角色信息 | 支持千人账号 |
| 登录/登出 | 客户端鉴权、连接管理、角色上线/下线 | 支持千人反复登录登出 |
| 移动同步 | 同地图角色间的位置广播 | 支持千人同图同时移动广播 |
| 数据持久化 | 角色信息、位置信息的持久化存储 | 高可靠、低延迟 |

### 1.2 性能指标要求

| 指标 | 要求 |
|------|------|
| 并发在线 | ≥ 1000 人同地图同时在线 |
| 登录登出 | 1000 人反复登录登出 |
| 移动广播 | 千人同时移动、位置同步广播 |
| 压测方式 | 机器人模拟客户端上行协议 |

### 1.3 关键挑战

1. **高并发连接**：单进程承载千级 TCP 长连接，IO 模型选择关键
2. **AOI 视野同步**：千人同图时，O(n²) 的全量广播不可行，需 AOI 剪枝
3. **服务拆分粒度**：过度拆分增加内网延迟，拆分不足影响横向扩展
4. **数据一致性**：角色位置等频繁更新的数据需要高效的持久化策略
5. **断线重连**：网络不稳定时需支持连接恢复和状态续传

## 三、关键技术方案

### 3.1 网络 IO 模型

#### 方案选型对比

| 方案 | 跨平台 | 性能 | 开发效率 | 推荐度 |
|------|--------|------|---------|-------|
| C++ + Boost.Asio | 优秀 | 高 | 低 | ⭐⭐⭐ |
| C++ + libuv | 优秀 | 高 | 低 | ⭐⭐⭐ |
| Go + goroutine | 良好 | 中高 | 高 | ⭐⭐⭐⭐⭐ |
| Java Netty | 优秀 | 高 | 中 | ⭐⭐ |
| Python asyncio | 优秀 | 中 | 高 | ⭐ |

**推荐方案：Go 语言**

理由：
- goroutine 天然适合千级连接管理，每个连接一个 goroutine，代码简洁
- 无需手动管理 epoll 事件循环
- 内置 pprof 性能分析工具，满足进阶需求
- 编译为单二进制，部署简单
- 社区成熟，有优秀的网络库（kcp、protoactor）

### 3.2 协议设计

#### 帧格式

```
┌────────┬────────┬──────────┬─────────┬────────┐
│ Length │ MsgID  │ Sequence │ ErrCode │  Body  │
│  4 B   │  2 B   │   4 B    │   2 B   │ N B    │
└────────┴────────┴──────────┴─────────┴────────┘
```

- **Length**：4 字节，整个包长度（含自身）
- **MsgID**：2 字节，消息类型标识
- **Sequence**：4 字节，序列号用于请求-响应配对
- **ErrCode**：2 字节，错误码（响应包使用）
- **Body**：变长，Protobuf 编码

#### 消息类型定义

```
enum MsgID {
  // 登录/鉴权
  C2L_LoginReq     = 0x0101;
  L2C_LoginRsp     = 0x0102;
  C2L_CreateRole   = 0x0103;
  L2C_CreateRoleRsp = 0x0104;

  // 心跳
  C2L_Heartbeat    = 0x0105;

  // 场景/移动
  C2S_EnterScene   = 0x0201;
  S2C_EnterSceneRsp = 0x0202;
  C2S_MoveReq      = 0x0203;
  S2C_MoveBroadcast = 0x0204;

  // 视野
  S2C_AOIEnter     = 0x0301;  // 新实体进入视野
  S2C_AOILeave     = 0x0302;  // 实体离开视野
}
```

### 3.4 AOI 视野同步方案

#### 方案对比

| 方案 | 原理 | 时间复杂度 | 适合场景 | 缺点 |
|------|------|-----------|---------|------|
| **网格法 (Grid)** | 将地图划分为等大格子，只广播相邻格子 | O(9n) - 最优 | **推荐**：均匀分布 | 格子大小需调整 |
| 十字链表法 | X/Y 方向有序链表 | O(√n) | 稀疏大世界 | 实现复杂、热点移动频繁重建 |
| 灯塔法 | 每个格子分配广播代理 | O(k) | 密集区域 | 代理节点管理开销大 |
| 九宫格法 | 只通知玩家周围 3×3 区域 | O(9n) | 中小规模 | 边界处理复杂 |

**推荐方案：网格法 (Grid-based AOI)**

- 地图划分为 N×N 个等大网格（如 100×100）
- 每个网格维护一个实体列表
- 玩家移动时：
  1. 更新所在网格
  2. 检测网格变化（是否跨格）
  3. 跨格时：通知新格子的玩家进入视野 / 旧格子的玩家离开视野
  4. 向当前所在网格 + 周围 8 个网格广播位置

```
地图 1000×1000，格子大小 100×100 → 10×10 网格

[ ][ ][ ][ ][ ][ ][ ][ ][ ][ ]
[ ][ ][ ][ ][ ][ ][ ][ ][ ][ ]
[ ][ ][★][ ][ ][ ][ ][ ][ ][ ]    ★ = 玩家所在格子
[ ][ ][▨][ ][ ][ ][ ][ ][ ][ ]    ▨ = 广播范围 (3×3)
[ ][ ][ ][ ][ ][ ][ ][ ][ ][ ]
[ ][ ][ ][ ][ ][ ][ ][ ][ ][ ]
[ ][ ][ ][ ][ ][ ][ ][ ][ ][ ]
```

#### 视野广播关键点

- 移动消息不做可靠送达（UDP 语义），使用最终一致性
- 进入/离开视野消息需要可靠送达（TCP 语义）
- 移动更新频率：≤ 20 次/秒（50ms 间隔）
- 可增加**移动预测**降低上行频率

### 3.5 数据持久化方案

#### 分层存储策略

```
                    ┌─────────────────────┐
                    │   Redis (Cache)      │  热数据、高吞吐
                    │  - 玩家在线状态      │  key: online:<uid>
                    │  - 当前位置          │  key: pos:<uid>
                    │  - Session Token     │  key: session:<token>
                    └─────────┬───────────┘
                              │ 异步落盘
                    ┌─────────▼───────────┐
                    │   MySQL / MongoDB    │  冷数据、可靠存储
                    │  - 账号信息          │  account_table
                    │  - 角色基础信息       │  role_table
                    │  - 位置历史(可选)     │  pos_history
                    └─────────────────────┘
```

#### 数据表设计（MySQL）

```sql
-- 账号表
CREATE TABLE accounts (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    username   VARCHAR(32) NOT NULL UNIQUE,
    password   VARCHAR(128) NOT NULL,  -- bcrypt hash
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 角色表
CREATE TABLE roles (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    account_id BIGINT NOT NULL,
    name       VARCHAR(16) NOT NULL,
    level      INT DEFAULT 1,
    map_id     INT DEFAULT 1,
    pos_x      DOUBLE DEFAULT 0.0,
    pos_y      DOUBLE DEFAULT 0.0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (account_id) REFERENCES accounts(id)
);
```

#### 缓存设计（Redis）

| Key 模式 | 类型 | 用途 | TTL |
|---------|------|------|-----|
| `session:<token>` | String | Session → {uid, lobby_addr} | 5min（续期） |
| `online:<uid>` | String | 在线状态 + 所在场景 | 在线期间 |
| `pos:<uid>` | Hash | {x, y, map_id, rot} | 在线期间 |
| `scene:<id>:players` | Set | 场景内玩家集合 | 在线期间 |

#### 落盘策略

- **写回策略 (Write-back)**：位置数据先写 Redis，定时批量刷入 MySQL
- **刷盘周期**：位置每 5s 批量写一次，关键操作（登录/登出/创建角色）实时写
- **Redis 崩毁恢复**：从 MySQL 恢复最近位置快照，允许秒级丢帧

## 五、技术选型总结

| 维度 | 选型 | 理由 |
|------|------|------|
| 开发语言 | Go 1.21+ | 高并发、低心智负担、内置 pprof |

| 协议 | 二进制 Length + Body | 解析开销低、适合游戏场景 |

## 七、进阶方向

1. **性能分析**：使用 Go pprof + flamegraph 定位热点函数
2. **UDP 协议**：移动消息使用 KCP 替代 TCP，降低广播延迟
3. **ECS 架构**：场景实体使用 Entity-Component-System 管理，提升 cache 友好性
4. **分布式扩展**：Lobby 按连接数水平扩展，Scene 按地图拆分
5. **Protobuf oneof**：利用 oneof 减少序列化体积
6. **共享内存**：同机 Scene 间通信使用共享内存替代 TCP
