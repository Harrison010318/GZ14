# GZ-14 游戏后台（局外系统）测试方案

> 版本：v1.0  
> 目标：覆盖功能正确性验证、性能指标验证、稳定性验证

---

## 一、测试目标

| 维度 | 目标 |
|------|------|
| 功能正确性 | 角色创建、登录/登出、移动同步完整流程符合预期 |
| 协议兼容性 | 客户端与服务端消息编解码一致 |
| 连接管理 | 心跳保活、断线重连、超时清理正确 |
| 并发性能 | 支持千人同图在线、千人同时登录、千人同时移动广播 |
| 稳定性 | 长时间运行无内存泄漏、无协程泄漏、无数据错乱 |
| 数据持久化 | 角色数据正确保存与恢复 |

## 四、测试用例设计

### 4.1 协议层测试

| 编号 | 用例名称 | 前置条件 | 操作步骤 | 预期结果 |
|------|---------|---------|---------|---------|
| PROTO-01 | 封包解包正确性 | 无 | 构造 LoginReq 消息 → 编码 → 解码 | 解码字段值与原始值完全一致 |
| PROTO-02 | 粘包处理 | 无 | 连续发送 3 个消息在同一次 TCP 读中 | 正确拆出 3 个独立消息 |

### 4.3 Scene 服务测试

#### 4.3.1 AOI 算法（单元测试）

| 编号 | 用例名称 | 前置条件 | 操作步骤 | 预期结果 |
|------|---------|---------|---------|---------|
| SCENE-001 | 玩家进入场景 | 地图网格已初始化 | 在 (150, 150) 位置加入一个玩家 | 周围格子 (100-200) 范围内玩家收到 AOIEnter 通知 |

| SCENE-003 | 跨格移动 | 玩家在格 A | 玩家从格 A 移动到格 B | 新邻居收到 AOIEnter，旧邻居收到 AOILeave |
| SCENE-004 | 格内移动 | 玩家在格 A | 同格内微移，未跨格 | 不触发 Enter/Leave，仅更新位置 |

| 编号 | 用例名称 | 前置条件 | 操作步骤 | 预期结果 |
|------|---------|---------|---------|---------|
| SCENE-009 | 正常移动广播 | 玩家 A、B 在同一视野 | A 发送移动请求 | B 收到 A 的 MoveBroadcast |
| SCENE-010 | 移动频率限制 | 玩家连续发送 100 次/s | 发送 100 次移动请求 | 服务端限频至 20 次/s，多余丢弃或节流 |

| SCENE-012 | 视野范围外移动不广播 | A 移动离开 B 的视野范围 | A 移动到远距离 | B 收到 AOILeave，不再收到移动广播 |

| 编号 | 用例名称 | 前置条件 | 操作步骤 | 预期结果 |
|------|---------|---------|---------|---------|
| DB-001 | 创建角色持久化 | 登录成功 | 创建角色 | MySQL 中新增角色记录 |

### 4.6 E2E 场景测试

| 编号 | 用例名称 | 操作步骤 | 预期结果 |
|------|---------|---------|---------|
| E2E-001 | 完整快乐路径 | 注册 → 创角 → 登录 → 进入场景 → 移动 → 登出 | 每一步返回成功，数据最终正确落库 |
| E2E-002 | 双角色同地图可见 | 客户端 A、B 登录到同地图同区域 | A 和 B 相互进入对方视野，能收到对方移动广播 |

## 五、性能测试方案

### 5.1 性能指标基线

| 指标 | 目标值 | 严重告警线 | 说明 |
|------|--------|-----------|------|
| 最大并发连接数 | ≥ 1000 | < 500 | 同时维持的 TCP 连接 |
| 登录吞吐量 | ≥ 200 QPS | < 50 QPS | 每秒完成登录次数 |
| 移动广播延迟 | < 50 ms | > 200 ms | 从收到移动到发出广播 |
| 广播吞吐量 | ≥ 5000 msg/s | < 1000 msg/s | 每秒发出的视野广播消息数 |
| CPU 使用率 | < 70% | > 90% | 服务端 CPU 整体使用率 |
| 内存使用 | < 2 GB | > 4 GB | 千人在线时 RSS |
| GC 暂停时间 | < 10 ms | > 50 ms | Go GC STW 时间（P99） |
| 压测端 CPU | < 80% | - | 确保瓶颈在服务端 |

### 5.2 场景一：千人登录风暴

**目的**：验证 Lobby 服务在高并发登录下的吞吐能力和稳定性

**前置条件**：
- 预先在数据库创建 1000 个账号（可通过脚本批量写入）

**步骤**：
1. 启动 1000 个 Bot 连接，每个 Bot 发送 LoginReq
2. 以 200 bot/s 的速度逐步启动，避免瞬间峰值为网络瓶颈
3. 每个 Bot 等待 LoginRsp 后记录耗时
4. 全部登录后，所有 Bot 发送 EnterSceneReq

**数据采集**：

| 采集项 | 方式 |
|--------|------|
| 登录耗时（avg / P50 / P95 / P99 / max） | Bot 端记录 |
| 登录成功率 | Bot 端统计 |
| 服务端 CPU / 内存曲线 | pprof / top |
| goroutine 数量 | pprof |
| DB 连接数 | MySQL 监控 |
| 每秒完成登录数（QPS） | 服务端 metrics |

**通过标准**：
- 登录成功率 ≥ 99.5%
- P99 登录耗时 < 2s
- 无 goroutine 泄漏（登录前后 goroutine 数量一致）
- 无内存持续增长

### 5.3 场景二：千人持续移动广播

**目的**：验证 Scene 服务在千人同图移动时的 AOI 性能和广播吞吐量

**前置条件**：
- 1000 个角色全部登录且在同一地图

**步骤**：
1. 让 1000 个 Bot 均匀分布在 10×10 网格中（约 10 人/格）
2. 每个 Bot 以 3~5 msg/s 的频率发送 MoveReq
3. 每次移动随机方向偏移 5~20 单位
4. 持续运行 5 分钟
5. 记录服务端性能数据

**数据采集**：

| 采集项 | 方式 |
|--------|------|
| 广播延迟（从收到 MoveReq 到发出广播） | 服务端插桩 |
| 广播消息吞吐量（msg/s） | 服务端统计 |
| AOI 单次查询耗时 | 服务端插桩 |
| CPU / 内存 | pprof |
| GC 统计 | `GODEBUG=gctrace=1` 或 pprof trace |
| 网卡出流量 | `netstat` / `iftop` |
| 广播消息丢失率 | Bot 端序列号连续性检测 |

**通过标准**：
- 广播延迟 P99 < 50ms
- CPU 使用率 < 70%
- 内存无明显增长（< 200MB 波动）
- Bot 接收广播序列号连续（无丢失）
- 广播吞吐量 ≥ 5000 msg/s

### 5.4 场景三：反复登录登出

**目的**：验证系统长时间、频繁登录登出下的稳定性，检测资源泄漏

**前置条件**：
- 1000 个账号存在

**步骤**：
1. 1000 个 Bot 循环执行：登录 → 进入场景 → 移动 30s → 登出
2. 等待全部登出完成立即开始下一轮
3. 循环 10 轮
4. 每轮结束后记录 goroutine 数量、内存、DB 连接

**数据采集**：

| 采集项 | 方式 |
|--------|------|
| 每轮完成时间 | Bot Manager 记录 |
| 每轮成功率 | Bot 统计 |
| goroutine 数量变化 | 每轮结束时采集 |
| 内存变化 | 每轮结束时采集 |
| MySQL 连接数变化 | 每轮结束时采集 |
| Redis 内存变化 | `INFO memory` |

**通过标准**：
- 每轮成功率 ≥ 99%
- 初始 vs 最终 goroutine 数量偏差 < 5%
- 无内存持续增长趋势
- MySQL / Redis 连接数稳定

### 5.5 场景四：混合压力（推荐饱和测试）

**目的**：模拟真实混合场景，验证系统综合承载能力

**步骤**：
1. 500 个 Bot 持续移动（行为同场景二）
2. 500 个 Bot 反复登录登出（行为同场景三）
3. 同时运行 10 分钟
4. 记录全部指标

**通过标准**：
- 移动广播延迟 P99 < 100ms（相比纯移动场景可放宽）
- 登录成功率 ≥ 99%
- 无进程崩溃或死锁
- 服务端无异常日志输出

### 5.6 场景五：长时间稳定性（可选）

**目的**：验证系统长时间运行的稳定性

**步骤**：
1. 500 个 Bot 保持在线 × 持续 4 小时
2. 以 1~3 msg/s 频率持续移动
3. 每 30 分钟记录一次指标
4. 第 2 小时加入 500 个 Bot 反复登录登出

**通过标准**：
- 4 小时内无重启、无崩溃
- 内存增长 < 30%
- 无异常日志

```go
type BotBehaviour int

const (
    Behaviour_LoginOnly      = iota  // 仅登录登出
    Behaviour_ContinuousMove         // 持续移动
    Behaviour_Mixed                  // 混合（默认）
    Behaviour_Reconnect              // 断线重连
```

### 6.3 Bot 配置参数

```go
type BotConfig struct {
    ServerAddr       string   // 服务端地址
    TotalBots        int      // Bot 总数

    Behaviour        string   // 行为模式

    ReconnectEnabled bool     // 是否测试断线重连
    ReportIntervalMs int      // 指标上报间隔
}
```

## 九、通过/不通过判定标准

### 9.1 功能测试通过标准
- 所有 P0 级用例通过率 100%
- 全部用例通过率 ≥ 90%
- 无阻塞性问题（P0 Bug = 0）

### 9.2 性能测试通过标准
| 场景 | 必须达标 | 争取达标 |
|------|---------|---------|
| 千人登录 | 成功率 ≥ 99%，P99 < 3s | 成功率 ≥ 99.9%，P99 < 1s |
| 千人移动 | 广播延迟 P99 < 100ms | 广播延迟 P99 < 50ms |
| 反复登录登出 | 10 轮无累积增长 | 20 轮无累积增长 |
| 混合压力 | 无崩溃，广播 P99 < 150ms | 无崩溃，广播 P99 < 100ms |
| 长时间稳定性 | 4h 无重启 | - |

### 9.3 最终结论判定

```
[通过]  所有必选测试项通过，核心性能指标不低于必达线
[有条件的通过]  功能全通过，性能指标部分未达必达线但有明确的优化路径
```
