# GZ-14 技术选型文档

> 游戏后台（局外系统）— 技术调研与选型结论

---

## 1. 开发语言：Go

| 因素 | 结论 |
|------|------|
| 网络并发 | goroutine 天然适配千级 TCP 长连接，每连接一线程模型简单 |
| 内存效率 | 千人在线预估内存 < 1GB，GC 压力可接受 |
| 开发效率 | 标准库 net 即可完成网络层，无需第三方框架 |
| 性能分析 | 内置 pprof + trace，满足进阶性能分析需求 |
| 部署 | 单二进制编译，无运行时依赖 |

## 2. 网络 IO 模型：Reactor + goroutine-per-connection

- 主 goroutine 做 Accept
- 每个连接分配独立 goroutine 处理读写
- 封包/解包在连接 goroutine 内完成，避免业务逻辑阻塞 IO
- 不在网络层引入额外的事件循环框架

## 3. 通信协议：二进制 Length-based 协议 + Protobuf

```
帧格式：
┌────────┬────────┬──────────┬─────────┬────────┐
│ Length │ MsgID  │ Sequence │ ErrCode │  Body  │
│  4 B   │  2 B   │   4 B    │   2 B   │ N B    │
└────────┴────────┴──────────┴─────────┴────────┘
```

- **Length**：4 字节，整包长度（含自身），解决 TCP 粘包
- **MsgID**：2 字节，消息路由标识
- **Sequence**：4 字节，请求-响应配对
- **ErrCode**：2 字节，响应状态码
- **Body**：Protobuf 序列化，跨语言兼容、解析高效

选择理由：Protobuf 相比 JSON 体积小 60%+，解析速度快 5-10 倍，适合游戏高频消息场景。

## 4. 服务架构：三服务拆分（Lobby / Scene / DB）

```
Client → Lobby Service ←→ Scene Service ←→ DB Service
          登录/鉴权          地图/AOI         数据持久化
          连接管理           移动广播
          会话维持           视野同步
```

| 服务 | 职责 | 为何独立 |
|------|------|---------|
| **Lobby** | 连接网关、登录鉴权、心跳保活、角色管理 | 长连接入口，需要独立扩缩容 |
| **Scene** | 地图逻辑、AOI 网格、位置同步、视野广播 | 核心性能敏感逻辑，独立优化 |
| **DB** | 账号/角色数据的读写封装 | 与缓存策略绑定，统一数据访问 |

服务间通信：内部自定义 TCP RPC，轻量无额外依赖。

## 5. AOI 算法：网格法 (Grid-based)

| 方案 | 选型 |
|------|------|
| 网格法 | ★ **选用** — 实现简单，千人场景每帧广播范围 O(9n)，可接受 |
| 十字链表 | ✗ 弃用 — 玩家密集移动时链表频繁重建 |
| 灯塔法 | ✗ 弃用 — 实现复杂，千级规模下收益不明显 |

参数预设：
- 地图大小：1000 × 1000 单位
- 网格大小：100 × 100 单位 → 10 × 10 网格
- 视野范围：玩家所在网格 + 周围 8 格
- 移动广播频率上限：20 次/秒（50ms 间隔）

## 6. 数据持久化：Redis + MySQL 双层

| 层级 | 技术 | 用途 |
|------|------|------|
| 热数据缓存 | **Redis** | Session Token、在线状态、实时位置 |
| 冷数据存储 | **MySQL** | 账号信息、角色存档、位置快照 |

- Session/位置数据先写 Redis 返回客户端，异步批量刷 MySQL
- 位置落盘周期 5s，允许秒级丢帧以换取写入性能
- 关键操作（创角、登录、登出）实时落 MySQL，不做延迟

### MySQL 设计

两张核心表：`accounts`（账号） + `roles`（角色）

## 7. 服务间序列化：Protobuf 内联（不引入 gRPC）

- 服务间通信复用客户端-服务端的 Protobuf 消息定义
- 减少协议转换开销
- 不引入 gRPC 避免 HTTP/2 帧开销和流控复杂性

## 8. 压测方案：自研 Bot

| 组件 | 说明 |
|------|------|
| Bot Manager | 管理 1000 个机器人生命周期 |
| Bot Agent | 模拟完整客户端行为：登录 → 移动 → 登出 |
| Metrics | 采集延迟、QPS、成功率 |
| Controller | 控流（如每秒启动 200 个机器人） |

不引入 JMeter/Locust 等通用压测工具，因其不适合 TCP 二进制协议场景。

## 9. 选型全景速览

| 维度 | 选型 | 一句话理由 |
|------|------|-----------|
| 语言 | Go | goroutine 并发模型匹配场景 |
| 网络 | net 标准库 | 轻量可控，千级连接无需第三方 |
| 协议 | Length + Protobuf | 粘包处理 + 高效序列化 |
| 架构 | Lobby / Scene / DB | 职责分离，独立演进 |
| AOI | 网格法 | 实现简单，千级可接受 |
| 缓存 | Redis | 高吞吐，适合位置等高频写 |
| 存储 | MySQL | 成熟稳定，关系语义匹配 |
| 压测 | 自研 Bot 工具 | TCP 协议兼容，灵活控制场景 |
